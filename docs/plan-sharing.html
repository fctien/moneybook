MoneyBook 多人共用與發票照片 — 可行性評估與實作規劃

2026-09-08 擬定 · 基準版本 v1.17.0 ·  基準 commit 5574cdd（工作區乾淨） ·  狀態：待拍板，尚未動工

0. 需求

  1. 僅需要簡易記帳功能
  2. 要提供多人能共用
  3. 能夠儲存發票，照相後儲存

問題：這些需求用 PWA 能完成嗎？

1. 結論先講

需求PWA 做得到嗎要付出什麼
1. 簡易記帳 做得到 幾乎零成本。功能早就有了，要做的是把股票／基金收起來，不是再寫新東西
2. 多人共用 做得到
但必須加後端		 本專案最大的一次架構改變。前端仍是純靜態檔， 但必須外接一個資料庫服務，且「資料只存在你的裝置上」這條原則會被打破
3. 發票照相儲存 做得到 純前端就能完成。拍照的程式碼現在就已經有了 （qrscan.js 的 capturePhoto()）。 只有「照片要不要跟著多人共用」會牽到需求 2

一句話：三項都可行，PWA 不是限制。真正的分水嶺是需求 2 —— 它把這個 App 從「單機工具」變成「有帳號的服務」。 需求 1 和 3 可以立刻做、不必等需求 2；需求 2 需要您先拍板兩件事（見第 9 節）。

2. 需求一：簡易記帳

現況其實是反過來的問題：記帳功能一開始就完成了， 後來長出股票（v1.3–v1.16）與基金（v1.15）兩大模組，介面因此變重。 「只要簡易記帳」不是要補功能，是要把後來長出來的東西收起來。

2.1 做法：加一個「簡易模式」開關，不刪程式碼

刪掉股票／基金做成開關（建議）
介面清爽度一樣一樣
已投入的 200 多項測試一併作廢全部保留
之後想用回來要從版控挖回來重接設定裡按一下
App 體積少約 100 KB不變 — 但股票模組本來就是 動態 import，沒開就不會載入，實際啟動速度沒有差別

既然沒開就不會下載，刪掉的唯一好處只剩「repo 比較小」， 代價卻是丟掉 v1.3 到 v1.17 累積的所有東西。不划算，改用開關。

2.2 具體改動

  • 設定頁新增「進階功能」區塊：股票、基金 兩個開關，預設關閉
  • 資產頁的三個分頁（帳戶／股票／基金）依開關決定要不要出現；只剩帳戶時不顯示分頁列
  • 已經有股票或基金資料的使用者，升級時自動維持開啟 — 不能因為改版就讓人以為資料不見了
  • 底部五個分頁維持不變（記帳／明細／資產／報表／設定）

估算：動到 views/settings.js、views/assets.js 與 store.js 的設定值，加 3–5 項測試。規模小。

3. 需求二：多人共用

3.1 為什麼 PWA 本身做不到

PWA 的離線能力靠 Service Worker（快取程式碼）與 IndexedDB（存資料）， 這兩者都綁在單一瀏覽器的單一來源上。 同一支手機換個瀏覽器就讀不到，更不用說換一台手機。 瀏覽器沒有任何 API 能讓兩台裝置直接看到彼此的 IndexedDB — 這是安全模型的根本，不是「還沒實作」。

所以多人共用一定要有一個大家都連得到的地方存資料。 問題不是「PWA 行不行」，而是「那個地方放哪裡」。

3.2 先排除三個「不用後端」的想法

想法結果原因
互相傳備份檔，用現有的「合併匯入」 不夠用 現有的 mergeAllData() 確實能合併，但要手動傳、手動匯入。 兩人同一天各記五筆，得記得誰傳給誰、誰匯入了沒 — 漏一次就對不起來，而且不會有任何提示
WebRTC 讓兩支手機直接連 不可行 WebRTC 仍需要一台伺服器幫忙牽線（所以還是有後端）， 而且兩個人必須同時開著 App。 記帳是各記各的 — 太太在早市記一筆時先生正在上班，這個前提不成立
把資料檔放共用的 iCloud／Google 雲端硬碟資料夾 不可行 網頁不能自行讀寫使用者的雲端硬碟。 File System Access API 在 iOS Safari 完全不支援， 且無論如何都要使用者每次手動挑檔案。改用 Drive API 則需要 OAuth — 繞一圈還是後端，只是換成 Google 的規則

3.3 後端選型

本專案的硬性條件：沒有 npm、沒有建置流程、沒有 CDN 相依，前端仍放 GitHub Pages。 這條件會直接篩掉一些選項。

方案能否只用 fetch評語
Supabase
（Postgres + Auth + Storage）		 可以 建議採用。資料、登入、檔案儲存三者都提供標準 REST， 全部用 fetch 打得到，一行 SDK 都不必載。 權限由資料庫本身的 Row Level Security 控制，前端拿不到不該拿的資料
Firebase
（Firestore）		 實務上不行 離線同步是它最強的地方，但那些能力都在 SDK 裡（壓縮後仍有數百 KB）。 要嘛引入 CDN、要嘛開始有建置流程 — 兩者都違反本專案既有的原則
Cloudflare
（Workers + D1 + R2）		 可以 免費額度大方，不會因為閒置被暫停。 但 API 要自己寫、自己維護、權限檢查也要自己寫 — 等於多養一個後端專案。列為備案
自架於 Render 可以 您已有 Render 的使用經驗。但免費方案閒置會休眠，冷啟動十幾秒 — 記一筆帳要等那麼久並不合理；資料庫也要自己備份。不建議

3.4 建議：Supabase ＋ 純 fetch，前端仍留在 GitHub Pages

前端的架構一個字都不用改 — 依舊是靜態檔、依舊 GitHub Pages、依舊沒有建置流程。 新增的只是一支 js/lib/cloud.js，裡面全是 fetch。

注意一個與直覺相反的地方：Supabase 的 anon key 是設計上就要公開的 （會出現在前端原始碼裡），安全性由 RLS 政策保證，不是靠把金鑰藏起來。

3.5 資料模型

共用的單位是帳本而不是「帳號」— 這樣一個人可以同時擁有「家庭共用帳」與「自己的私帳」。 

ledgers          帳本      id, name, owner_id, created_at
ledger_members   成員      ledger_id, user_id, role(owner/editor/viewer), joined_at
transactions     收支      id, ledger_id, date, amount_cents, category_id,
                           account_id, note, created_by, updated_at, deleted
accounts         帳戶      id, ledger_id, ..., updated_at, deleted
categories       分類      id, ledger_id, ..., updated_at, deleted
attachments      發票照片  id, ledger_id, tx_id, storage_path, bytes, updated_at, deleted

RLS 政策的核心只有一條：「這一列的 ledger_id 必須出現在我的 ledger_members 裡」。寫入另外檢查 role。

這是整個計畫風險最高的一點。RLS 寫錯等於別人的帳本被讀得到， 而且平常操作完全看不出異常。因此驗收必須有一項刻意的越權測試： 用 A 的 token 去讀 B 的帳本，必須拿到 0 筆而不是錯誤訊息 — 拿到 0 筆才代表政策真的生效，拿到錯誤訊息可能只是網址打錯。

3.6 同步怎麼做

不改寫現有的 IndexedDB 架構。本地依舊是唯一的讀取來源， 畫面切換依舊零延遲，離線依舊完全可用 — 只是多一層在背景推拉的同步層。 這也讓現有的 210 項測試原封不動。

機制做法為什麼
寄件匣（outbox） 每一次本地寫入，同時記一筆待送清單。連上網才送，送成功才清掉 離線記的帳不能掉。這是離線優先 App 的標準做法
墓碑（tombstone） 刪除改成標記 deleted=true，不真的移除 沒有墓碑的同步，刪掉的資料會從另一台裝置復活， 而且使用者只會覺得「我明明刪過了」
後寫贏（LWW） 比 updated_at，晚的蓋掉早的，逐筆比對 記帳的衝突極罕見 — 兩個人幾乎不會同時改同一筆。 為此引入 CRDT 之類的機制，複雜度遠大於收益
拉取用增量 只要 updated_at > 上次同步時間 的資料 每次全量拉會隨著年份累積愈來愈慢，而且吃流量

合併邏輯全部寫成純函式（js/lib/sync.js）： 輸入兩份資料、輸出合併結果，不碰網路也不碰資料庫 — 這樣才測得動，也才敢改。與 portfolio.js、funds.js 是同一個路數。

3.7 邀請怎麼運作

  1. 帳本擁有者按「邀請成員」，產生一組六位邀請碼（有效期 7 天，可撤銷）
  2. 對方註冊／登入後輸入邀請碼，即加入該帳本
  3. 成員清單可看到誰在裡面、各自的權限，擁有者可移除成員
  4. 明細每一筆顯示是誰記的 — 共用帳本裡這是必要資訊，否則對不上帳時無從查起

用邀請碼而不是「輸入對方 email 直接加入」：後者只要打錯一個字， 就把陌生人加進自己的家庭帳本，而且雙方都不會發現。

3.8 這件事會改掉專案的核心宣稱

README 現在最上面寫著「資料完全存在你自己的裝置裡，不上傳任何伺服器」。 一旦開始同步，這句話對共用帳本就不再成立。

建議的處理方式，也是我認為唯一誠實的做法：

  • 單機模式維持預設。不登入就跟現在一模一樣，一個位元組都不外傳
  • 雲端同步是使用者主動開啟的功能，開啟前明白告知資料會存到哪裡
  • README 與 App 內的說明同步改寫，不模糊帶過

順帶一提：開了同步之後，「每月手動備份」的壓力會小很多 — 手機掉了資料還在雲端。這是需求 2 的附加收穫。

3.9 中國大陸的連線問題（2026-09-08 查證）

如果有人要在中國大陸使用，上面的整套選型都不成立。 這不是速度快慢的問題，是連不連得上的問題。
服務大陸可用性依據
Supabase 被封鎖 官方 repo 有長期未解的 issue：網站與 API 都被 GFW 擋下， magic link 請求沒有回應、Realtime 連線逾時。目前無中國區節點
Firebase（Google） 完全封鎖 Google 全域名封鎖，沒有例外
Cloudflare Workers 不可靠 workers.dev 在封鎖清單、DNS 被污染。 改用自訂網域「有些人連得到、有些人不行」— 依 ISP 而異，不能當方案
GitHub Pages（目前的前端） 慢且不穩 沒有全面封鎖，但時通時不通。連前端網頁本身都進不去

換句話說：現在這個 App 在中國大陸連打開都有問題，不只是同步不了。

3.10 要涵蓋大陸時的兩條路

境內雲 ＋ ICP 備案香港節點（免備案）
大陸連線最快最穩連得到，但延遲較高、丟包較多
手續要 ICP 備案 — 需中國實名主體、約 20 天審核， 台灣個人辦理相當麻煩不需要備案，買了就能用
費用伺服器費用輕量伺服器約每月 25 人民幣起
內容監管備案後受監管不受
工作量兩條路都要自己寫後端 — Supabase 幫忙做掉的登入、權限、REST API、備份，全部得自己來。 比接 Supabase 多出約一倍的工作量，而且是長期的維運責任

記帳的同步量極小（一次幾十 KB），香港節點的延遲與丟包對這個用途其實可以接受 — 它不是影音串流。因此若真的需要涵蓋大陸，香港節點是較務實的折衷。

3.11 但先分清楚是哪一種情境

情境建議
偶爾出差／短期停留大陸 不必為它改架構。本 App 是離線優先 — 在大陸照樣能記帳，只是同步不上去，回台灣後自動補送。 這正是離線優先架構的天然好處。
前提是：同步失敗絕不能擋住記帳（已列為第 7 節的風險對策）
有人長住大陸、要日常共用 Supabase 出局，整個選型改成香港節點自架， 前端與後端放同一台。成本從零變成每月約新台幣 110 元， 且要自己維護。這是目前唯一能同時服務兩岸的做法

4. 需求三：發票照相儲存

這一項純前端就能做完，而且底子已經打好了。

4.1 拍照：現成的

js/lib/qrscan.js 的 capturePhoto() 已經在用 <input type="file" accept="image/*" capture="environment"> 叫出系統相機。 當初為了掃發票 QR 而寫，直接拿來存照片即可。

當初刻意不用 getUserMedia 的理由（iOS 安裝成 PWA 後權限不被記住、 會反覆跳授權、iOS 26 有畫面轉 90 度的問題）在這裡一樣成立，維持原做法。

4.2 壓縮：一定要做

不壓縮壓縮後
單張大小iPhone 原檔 2–5 MB約 250–400 KB
一年 500 張1–2.5 GB約 150 MB
發票文字看不看得清清楚清楚（長邊 1600px 足以看清品項與金額）

做法：createImageBitmap → canvas 縮到長邊 1600px → toBlob('image/jpeg', 0.75)。純瀏覽器 API，不需要任何函式庫。 另存一張 200px 縮圖供清單顯示 — 明細頁一次載入幾十張原圖會很卡。

不用 WebP：體積確實更小，但發票這種只會存進去、偶爾拿出來看的資料， 相容性（舊 iOS、分享出去給別人看）比省那三成體積重要。

4.3 存哪裡

本地 IndexedDB雲端 Storage
要不要後端不用要（隨需求 2 一起）
其他人看得到看不到看得到
手機掉了照片全沒還在
離線能看能能（本地留快取）

建議兩者都做，先本地後雲端：階段 2 先做純本地版本（不必等後端，可以馬上用）， 階段 5 再把照片接上雲端，本地保留一份當快取。

iOS 的儲存空間會被回收。加到主畫面的 PWA 雖然比一般網頁安全， 但手機空間吃緊時系統仍可能清掉網站資料，而且不會有任何警告。 純本地存照片時要在設定頁顯示已用空間（navigator.storage.estimate()）， 並呼叫 navigator.storage.persist() 申請常駐 （Android 會給，iOS 目前不保證）。這也是「照片最終應該上雲端」的主要理由。

4.4 與現有掃描的整合

拍一張照，同時做兩件事 — 這是這個功能最順的地方：

  1. 解 QR：拿到日期、總金額、品項（現有功能，已完成）
  2. 存照片：壓縮後與該筆交易關聯（新增）

QR 解不出來也不要緊 — 照片照樣存下來，金額改由使用者自己填。 這與 scan.js 現有的設計原則一致：解不出品項不視為失敗。 手寫收據、國外的收據沒有台灣的電子發票 QR，這條路讓它們也存得進來。

4.5 備份要改

照片不能塞進現有的 JSON 備份檔。 轉成 base64 會膨脹三分之一，500 張照片會產出一個 200 MB 的 JSON — 手機上光是產生這個字串就可能直接當掉。

做法：拆成兩種匯出。

  • 資料備份（現有的 JSON）：維持不變，照片只存路徑與 id，不含影像
  • 照片匯出（新增）：分批打包下載，或直接倚賴雲端那一份

還原時若照片檔不在，要明確顯示「照片未包含在此備份中」， 而不是顯示一個破圖 — 使用者必須分得出「照片沒了」與「照片載入失敗」。

5. 分階段計畫

每一階段都能獨立交付、獨立驗收，中途喊停也不會留下半成品。

階段版本內容要後端規模
1. 簡易模式v1.18.0 股票／基金收進設定開關，預設關閉；已有資料者自動維持開啟 不用小
2. 發票照片（本地）v1.19.0 拍照 → 壓縮 → 存 IndexedDB（DB v4）→ 明細顯示縮圖 → 點開放大； 與 QR 掃描整合；空間用量顯示；備份策略調整 不用中
3. 帳號與後端v2.0.0 Supabase 專案建立、資料表、RLS 政策、註冊／登入、 js/lib/cloud.js、同步層 js/lib/sync.js （寄件匣 + 墓碑 + 後寫贏） 要大
4. 共用帳本v2.1.0 帳本切換、邀請碼、成員與權限、每筆顯示記帳人 要中
5. 照片上雲v2.2.0 照片同步到 Storage、離線上傳佇列、簽名網址、配額顯示 要中

階段 1 與 2 可以現在就開始 — 它們不依賴任何決策，做完就是可用的成果。 階段 3 之前需要您先回答第 9 節的問題。

把「帳號與後端」（階段 3）跟「共用帳本」（階段 4）分開，是因為前者是地基、後者是功能。 地基沒鋪穩就往上蓋，出問題時會分不清是同步錯了還是權限錯了。 階段 3 結束時的驗收目標只有一個：同一個人的兩台裝置，資料能對得起來。

6. 測試計畫

依專案慣例，能寫成純函式的一律純函式，用 node --test 跑。

對象怎麼測
lib/sync.js 合併邏輯 純函式單元測試。必測情境：兩邊離線各記三筆後同時上線、 一邊刪一邊改同一筆、同一筆在兩邊都被改、 時鐘不同步（手機時間慢五分鐘）
影像壓縮 尺寸上限、長寬比維持、EXIF 方向（直拍的發票不能變成橫的）、 壓縮後仍解得出 QR
RLS 權限 整合測試，不可省略。用 A 的 token 讀 B 的帳本必須得到 0 筆； viewer 角色寫入必須被拒
DB v3 → v4 升級 既有資料完全不動；舊版備份（沒有 attachments 欄位）仍能還原。 這兩項在股票模組升 v2 時就寫過，照同一個模式補上
端對端 沿用既有的 Playwright 手法：兩個瀏覽器 context 模擬兩個人， A 記一筆 → B 重新整理 → 看得到

特別提醒（來自 dev-log 2026-09-05 §10.4 的教訓）： 改完檔案要先清 Service Worker 快取再重載，順序反了會看到舊版而以為修正沒生效。 同步功能牽涉多台裝置，這個坑踩下去會更難察覺。

7. 風險

風險影響對策
RLS 寫錯 別人的帳目被讀到，而且平常完全看不出來 越權測試列為必要驗收項目；政策先寫「全部拒絕」再逐條開放
同步造成資料重複或消失 比沒有同步更糟 — 使用者會不再信任整個 App 墓碑 + 逐筆後寫贏；上線前先跑一段只讀不寫的影子同步，比對兩邊差異
免費專案閒置會被暫停 久沒用之後打開，同步失敗 每天有人記帳就不會觸發。更重要的是： 同步失敗時 App 必須照常能用， 只在角落提示「尚未同步」，絕不可擋住記帳
免費額度用完 主要是照片佔的儲存空間 設定頁顯示用量，接近上限時提示。文字資料量極小，不會是瓶頸
iOS 清掉本地照片 階段 2（純本地）時照片可能無聲消失 storage.persist() ＋ 用量顯示 ＋ 說明；階段 5 上雲後根本解決
隱私原則改變 專案的核心宣稱不再成立 單機模式維持預設；同步為主動開啟；README 誠實改寫

8. 費用：免費額度到底夠不夠

Supabase 免費方案的額度（2026-09-08 查證），對照一個家庭 3–5 人的實際用量：

項目免費額度家庭一年用量會不會用完
資料庫容量500 MB 一筆交易約 200 bytes，一年一萬筆 ≈ 2 MB 不可能
夠用兩百年以上
檔案儲存1 GB 照片壓縮後約 300 KB／張 → 約 3,300 張 唯一會滿的
每月 40 張約可用六至七年
月流量5 GB 每人每天同步幾十 KB，一個月幾 MB 不可能
月活躍用戶50,0003–5 人 不可能
專案數2 個1 個 不會

所以第 7 節說的「免費額度用完」實際上只有一件事：發票照片存滿 1 GB， 其他四項的差距是好幾個數量級，不必擔心。

而且用完不是資料消失，是新照片傳不上去。對策： 設定頁顯示已用比例，接近上限時提示，並提供「匯出舊照片後刪除」。 升級付費方案是每月 25 美元 — 對家庭記帳並不划算，刪舊照片實際得多。

8.1 另一個要注意的限制：閒置一週會暫停

免費專案閒置一週會被暫停，暫停後要到後台手動恢復。 每天有人記帳就不會觸發，但這也再次說明第 7 節那條對策為什麼重要： 同步失敗時 App 必須照常能用。

額度數字為 2026-09-08 查證，日後可能調整。 規劃時不把免費額度當成保證 — 所以設定頁要顯示用量，讓使用者自己看得到，而不是某天突然寫不進去。

9. 需要您先拍板

  1. 接受「共用帳本的資料會存到雲端」嗎？
    這是需求 2 無法迴避的代價。若不接受，多人共用就只能停在 「手動互傳備份檔」的程度 — 我不建議，那個做法漏一次就對不起來。
  2. 後端用 Supabase 可以嗎？
    建議它的理由是「不必引入任何 SDK，前端維持純靜態」。 備案是 Cloudflare（免費額度較好、不會被暫停，但 API 要自己寫自己維護）。
  3. 股票與基金要「收起來」還是「刪掉」？
    建議收起來（第 2 節）。反正沒開就不會載入，留著不影響效能。
  4. 需要涵蓋中國大陸嗎？是「偶爾出差」還是「有人長住」？
    這一題會直接推翻第 2 題的答案 — Supabase 在大陸被封鎖（見 3.9 節）。 偶爾出差不必改架構（離線照樣記帳）；有人長住則要改成香港節點自架， 工作量與長期維運責任都大幅增加。
  5. 要先做哪一段？
    建議 階段 1 → 2 先走，這兩段不需要任何後端， 做完您馬上就有「清爽的記帳 ＋ 發票存照片」可以用。 多人共用（階段 3–5）是另一個量級的工程，值得單獨開始。
