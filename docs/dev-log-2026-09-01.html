1. 需求演進

需求分三輪收斂，每一輪都讓架構大幅簡化：

輪次使用者需求對應架構
初始 記帳 + 資產紀錄，手機與電腦都要能用 評估五種方案，建議 PWA + Supabase 雲端同步
第二輪 資料要純本機不同步，但仍要全套功能含 CSV 匯入 指出「純本機」與「跨裝置」互斥，改提自架方案：
FastAPI + SQLite + Tailscale + 離線佇列
最終 只要手機單機能用，資產直接手動輸入 後端、同步、CSV 匯入全部拿掉。
純前端靜態 PWA + IndexedDB

最終方案不需要 npm、不需要建置流程、不需要伺服器，也沒有任何 CDN 相依。

2. 主要架構決策

2.1 金額用整數「分」儲存，且解析走純字串路徑

記帳程式最忌浮點誤差累積。第一版 parseAmount 用了 Number(value.toFixed(2)) * 100， 測試立刻抓到 '1.005' 解析成 100 而非 101 —— 因為 1.005 在 IEEE 754 下實際是 1.00499…。 改為直接切分整數與小數字串、取第三位小數做四捨五入，完全不碰浮點乘法。

2.2 日期不使用 toISOString()

它會轉成 UTC，在台灣（UTC+8）會讓凌晨八點前記的帳掉到前一天。全程改用本地時區的 YYYY-MM-DD 字串。

2.3 轉帳不計入收支統計

還卡費、把錢轉去定存這類動作只是搬錢。若計入收支，月報表會被大幅灌水，日均支出也失真。

2.4 帳戶分兩種估值方式

方式適用餘額來源
自動累算 tracked現金、銀行、信用卡期初餘額 + 每筆交易加減
手動估值 manual股票、不動產、保單、貸款使用者填的數字，不受交易影響

股票市值與房價無法靠記帳推算，只能定期手動更新；而現金若也要手動填，記帳就失去意義。

2.5 圖表自己用 Canvas 畫

引入 Chart.js 這類 CDN 套件會讓 App 在飛航模式下變成一片空白，與「完全離線可用」的前提衝突。 三種圖（長條、甜甜圈、折線）自繪約 200 行，並依 devicePixelRatio 放大畫布避免手機上線條糊掉。

3. 測試中發現並修正的缺陷

缺陷 1：算式解析把減號吃進數字，導致 100-30 完全無法計算

發現方式
node 單元測試 evaluateExpression 回傳 null
根因
tokenizer 樣式寫成 /-?\d*\.?\d+|[+\-*/]/g， 對 "100-30" 會切成 ["100", "-30"] 兩個數字而少掉運算子， 後續取運算元時得到 undefined
修正
數字樣式移除前導負號，改在解析開頭單獨處理負號
影響
高。記帳頁的算式輸入是核心功能，減法完全不能用

缺陷 2：圖表完全依賴 requestAnimationFrame，rAF 停滯時永遠畫不出來

發現方式
瀏覽器實測時三張圖 paintedPct: 0， 且 canvas bitmap 仍是 HTML 預設的 300×170，代表 setupCanvas 從未執行
根因
實測證實 rAF 在該環境永不觸發（即使 document.hidden === false）。 更糟的是 redrawQueued 旗標會卡在 true，把後續每一次重繪請求都吞掉
修正
rAF 與 setTimeout(120ms) 雙軌排程，先觸發者執行並取消另一個； 另加 visibilitychange 監聽，從背景回前景時補畫一次
影響
高。分頁移到背景、部分 WebView、iOS PWA 從凍結恢復都可能踩到， 且一旦踩到就是永久性的空白圖表

同樣的缺陷也出現在彈出面板的滑入動畫 —— rAF 不觸發時面板會永遠停在畫面外， 使用者按了按鈕卻毫無反應。已改用計時器觸發。

缺陷 3：手動估值的帳戶出現在記帳選單，記上去的錢會憑空消失

發現方式
手機尺寸截圖檢查時，發現帳戶列出現「台積電持股」與「房貸」
根因
記帳頁用了 activeAccounts()，未區分估值方式。 而測試已證實手動估值帳戶的餘額固定等於使用者填的數字， 記在上面的交易不會改變任何餘額
修正
新增 postableAccounts() 只回傳自動累算的帳戶， 記帳與轉帳（含轉入端）一律改用它；資產頁補上說明文字
影響
中高。不會造成程式錯誤，但會讓使用者記出一筆對不起來的帳且毫無提示

缺陷 4：備份備援路徑的狀態回報不誠實

發現方式
實測「複製到剪貼簿」在無使用者手勢時被瀏覽器擋下，正確退回文字備援， 但備份狀態列仍停在「尚未備份過」且無法更新
取捨
自動標記為已備份是錯的 —— 內容只是顯示出來，使用者未必真的存走了， 標記成功會讓人誤以為安全。改為在備援面板加一個「我已複製並保存」由使用者自己確認
順帶修正
saveTextFile 原本把「使用者取消分享」與「存檔失敗」都回報為 failed， 會在使用者主動取消時跳出錯誤訊息。已拆成 cancelled 與 failed

4. 測試涵蓋範圍

node 單元測試（38 項）

執行：node --test tests/lib.test.js

  • 金額解析：全形數字、千分位、無效輸入回 null 而非 0
  • 浮點誤差防護：19.99、0.07、1.005
  • 算式運算：乘法優先、除以零、拒絕任意程式碼
  • 日期：本地時區、閏年、不存在日期、跨年月份位移
  • 統計：餘額累加、轉帳不計收支、分類百分比合計 100%
  • 驗證：金額 ≤ 0、轉給自己、參照不存在的帳戶
  • 備份：往返一致性、壞資料逐筆跳過、CSV 逸出與 BOM

瀏覽器整合測試（39 項）

開啟 test.html，使用獨立資料庫，不影響正式資料

  • IndexedDB 建立、seed、重複初始化不重複塞入
  • 記帳寫入後重新載入仍存在
  • 信用卡消費呈現為負債、轉帳同時加減兩端
  • 手動估值帳戶不受干擾交易影響
  • 封存帳戶不列入淨資產
  • 同日快照覆蓋而非累積
  • 有交易的帳戶／分類拒絕刪除
  • 匯出 → 清空 → 還原後資料完全一致（含淨資產金額）
  • 合併匯入不刪除既有資料
測試環境限制：預覽窗格處於隱藏狀態時，指標點擊工具無法運作， 互動流程改以 JavaScript 派發同等事件驅動（選分類 → 輸入算式 → 送出 → 驗證明細與月結餘）。 圖表則以 getImageData 統計非透明像素比例來確認確實有繪製內容。

5. 實測驗證的使用者流程

  1. 首次開啟 → 顯示引導說明（資料存在哪裡、為何要備份）
  2. 記帳頁選「飲食」→ 輸入 35+50 → 即時顯示 = 85 → 送出
  3. 明細頁出現該筆紀錄，月摘要顯示「支出 85／結餘 -85」通過
  4. 資產頁新增「台積電持股」（選投資 → 自動切換為手動估值）1,500,000
  5. 資產頁新增「房貸」-6,000,000
  6. 淨資產正確顯示 -NT$4,500,085，資產與負債自動分組通過
  7. 儲存快照 → 報表頁三張圖正確繪製（bitmap 638×362，符合 dpr 2 的高解析度）通過
  8. 設定頁匯出備份 → 內容含 4 帳戶／16 分類／1 交易／1 快照通過
  9. 確認備份後狀態列由黃色警告轉為「✅ 上次備份：9/1（0 天前）」通過

版面實測（375×812 視窗）：記帳頁三段式佈局無重疊，鍵盤與送出鍵完整落在可視範圍內。 淺色與深色模式皆已檢視。

6. 已知限制與後續可做的事

  • 單機無同步：這是使用者明確選擇的取捨。換手機必須透過匯出／匯入備份檔轉移。
  • 備份是唯一救援手段：App 已在超過 30 天未備份時顯示警告，但無法強制。
  • 未做 CSV 匯入：依使用者決定移除，僅保留 CSV 匯出。
  • 可加：預算上限提醒、定期自動記帳（房租、訂閱）、多幣別。
