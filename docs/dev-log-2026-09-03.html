2.3 過程中的一次假警報

現象：按下「完成」後，明細頁顯示「本月還沒有任何紀錄」

初判
疑似存檔失敗或畫面未更新
查證
直接讀取 IndexedDB，發現該筆交易確實已寫入（amount 17000 分 = NT$170）
真因
自動化腳本把「按完成」與「切到明細頁」放在同一個批次內連續送出， submit() 是 async，await store.saveTransaction() 尚未完成， 明細頁就先讀了狀態
結論
非程式缺陷，是測試腳本的時序問題。分開操作後各頁數字全部正確
另一個一開始誤判的點：分類按鈕的 element ref 在關閉首次引導對話框後會重新產生， 沿用舊 ref 會點到失效節點。重新讀取頁面後即正常。

2.4 啟用 PWA 時發現的兩個真實缺陷

使用者要求「啟用 PWA」。實測發現 Service Worker 根本沒有註冊 （navigator.serviceWorker.getRegistration() 回傳 undefined， caches.keys() 為空陣列）。追查後找到兩個獨立的缺陷，兩個都會讓離線功能完全失效。

缺陷一：Service Worker 註冊時機錯誤（js/app.js）

原始程式碼
globalThis.addEventListener('load', () => { navigator.serviceWorker.register(...) })
問題
app.js 以 <script type="module"> 載入，等同 defer； 而 registerServiceWorker() 又是在 main() 裡 await store.init() 之後才呼叫。 執行到那一行時 load 事件早已觸發完畢， 此時才掛上監聽器，它永遠不會被呼叫。
後果
SW 從未註冊 → 沒有離線快取、沒有更新提示、瀏覽器也不認為這是可安裝的 PWA
修正
先檢查 document.readyState：已是 complete 就直接註冊， 否則才等 load（並加上 { once: true }）

缺陷二：開發伺服器單執行緒，被 SW 安裝流程塞死（tools/serve.py）

原始程式碼
socketserver.TCPServer（單執行緒）
問題
SW 在 install 階段會一次抓取整份 app shell（22 個檔案）， 瀏覽器同時開多條 keep-alive 連線平行下載。 單執行緒伺服器只能一條一條處理，前一條連線未關閉就無法接受下一條。
後果
伺服器完全停止回應（curl 逾時、頁面變成 chrome-error://chromewebdata/），修好缺陷一之後 PWA 仍然裝不起來
修正
改用 socketserver.ThreadingTCPServer， 設定 daemon_threads = True、allow_reuse_address = True

3.1 新增 GitHub Pages 自動部署

新增 .github/workflows/deploy.yml，推上 main 即自動：

  1. 先跑測試 — node --test 沒過就不部署，避免把壞掉的版本推到手機上
  2. 用 commit SHA 蓋掉 CACHE_VERSION — 這是關鍵一步
  3. 產生 version.json 記錄 commit 與建置時間

6. 新功能：掃電子發票（v1.1.0）

6.1 為什麼不做 OCR

使用者原本的需求是「拍收據 → OCR 辨識品項」。查證後認定 OCR 是繞遠路：

  • Tesseract.js 中文品質不佳，熱感應紙的小字、褪色、緊密行距只會更糟
  • 語言檔約 20 MB，全部塞進離線快取，App 體積會膨脹十倍以上
  • 品質好的雲端 OCR 都要把照片送上伺服器，直接牴觸「資料不離開裝置」的原則

關鍵發現：台灣的電子發票證明聯底部有兩個 QR Code， 品名、數量、單價本來就以數位形式編碼在右方條碼裡。 直接解碼是精確值，沒有辨識誤差，而且完全在本機完成。

6.2 規格來源

依財政部財政資訊中心「電子發票證明聯一維及二維條碼規格說明」v1.9 實作。 左方前 77 碼為固定欄位，其後以冒號分隔： 

發票字軌(10) 開立日期(7) 隨機碼(4) 銷售額(8,hex) 總計額(8,hex)
買方統編(8) 賣方統編(8) 加密驗證(24)                     ← 合計 77 碼
: 營業人自行使用區(10) : 條碼記載品目筆數 : 發票品目總筆數
: 中文編碼參數(0=Big5 1=UTF-8 2=Base64) : 品名 : 數量 : 單價 : …

右方：前 2 碼固定 "**"，其後接續左方放不下的品目資訊

6.3 為什麼用拍照而不是即時相機

iOS 上安裝成主畫面 App 後，getUserMedia 的權限不會被記住、會反覆跳授權， iOS 26 還有畫面轉 90 度的問題。改用 <input type="file" capture="environment"> 叫出系統相機拍一張靜態照片再從照片解碼，完全避開這些坑，也不需要任何權限提示。 桌機瀏覽器會自動退化成選檔案，同一套程式碼兩邊都能用。

一張發票有兩個 QR，而 jsQR 一次只回傳一個。 解法是找到第一個後，用它回傳的 location 把該區域塗白再掃一次。 另外由 1280 → 1920 → 2560 逐步提高解析度重試 —— 太低掃不到小條碼，太高在手機上慢得離譜。

6.4 測試抓到的兩個真缺陷

缺陷一：Base64 編碼時，數量與單價也被拿去解碼

發現於
Node 單元測試（第一次執行就 24/25，這題掛掉）
原因
規格中的「中文編碼參數」只作用在品名，數量與單價是十進位明碼。 我對每個欄位都做了 Base64 解碼，而 '35' 剛好是合法的 Base64，被解成亂碼
修正
把解碼移進 readItems，只對品名欄位解碼

缺陷二：UTF-8 品名以位元組傳入時變成亂碼

發現於
瀏覽器端實測，畫面上顯示「é®®å¥¶è¶」而不是「鮮奶茶」
為什麼單元測試沒抓到
Node 測試那時傳的是字串，而 jsQR 實際回傳的是 binaryData 位元組 —— 兩者走的是不同分支
原因
為了讓位元組與字元位置一對一對齊，內部是用 latin1 逐位元組轉字元。 那份文字對 ASCII 正確、對中文則是亂碼。decodeSegment 只在 Big5 時走 TextDecoder， UTF-8 直接回傳了那份 latin1 文字
修正
只要拿得到原始位元組就一律走 TextDecoder，不論 Big5 或 UTF-8
補強
加了 2 項迴歸測試，專門覆蓋「以位元組傳入」的實際形態，含跨左右條碼接續的多位元組字元
過程中還有一次假警報：修好缺陷二後重新整理，畫面仍是亂碼。 原因是 Service Worker 的 cache-first 提供了舊版程式碼 —— 開發伺服器雖然送 Cache-Control: no-store，但 SW 的快取在它之前就攔截了。 清掉快取與註冊後即正常。這也再次印證了 CACHE_VERSION 的必要性。
