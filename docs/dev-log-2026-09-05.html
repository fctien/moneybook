3. 過程中修掉的兩個問題

問題一：捲動指令完全沒有作用

現象
對 .view--report 設 scrollTop 後畫面紋風不動， 報表頁下半部的分類佔比與趨勢圖都拍不到
原因
可捲動的是外層的 #main，view 本身的 overflow-y 是 visible、scrollHeight 等於 clientHeight，對它設 scrollTop 沒有任何效果
修正
加上 scroll_main()，一律對 #main 操作， 並以比例而非絕對像素指定位置
怎麼發現的
寫腳本前先在瀏覽器實測每個選擇器，比對 scrollHeight 與 clientHeight 才發現 — 若直接跑腳本，只會得到三張看起來「沒捲動」但不會報錯的截圖

問題二：淨資產趨勢線是一條平線

現象
趨勢圖畫出來完全水平，下方顯示「增加 NT$0」
原因
示範資料用 store.takeSnapshot() 產生五筆快照， 但這個函式一律記錄「當下」的淨資產 — 不管指定哪一天，五筆數值完全相同
修正
改為直接 db.put() 寫入六筆遞增的快照 （2026-04 至 09，淨資產 52 萬 → 62.3 萬）
結果
趨勢線正確呈現上升，並顯示「4/1 至 9/5：增加 NT$103,220」

這兩個都不是 App 的缺陷，是示範腳本自身的問題。 先做一張十六宮格的截圖總覽再逐一檢視，比一張張看快得多，也是這樣才發現趨勢線不對。

7. 股票模組 第一階段（v1.3.0）

依 docs/plan-stocks.html 的規劃執行第一階段： 資料模型、手動輸入、部位與損益計算、純函式測試。 第二至四階段（CSV 匯入、自動抓價、圖表）尚未動工。

7.1 核心計算 js/lib/portfolio.js

設計理由
持股部位由交易紀錄推算，不另存一份 存兩份遲早會對不起來，而且對不起來時無法判斷哪一份才是對的。 與本專案「金額用整數分儲存」同一種考量：把誤差來源從根本移除
加權平均成本法 台灣券商對帳單的標準做法，數字能跟券商 App 對得起來。此決定之後不要改
賣出成本用 totalCost 依比例攤 先算出平均成本再乘回去會累積除不盡的誤差。實測反覆進出二十次後， 成本與損益仍精確歸零
沒有報價時回傳 null 而非 0 0 會被誤讀成「這檔歸零了」
少一檔報價就標記整體為不完整 少算一檔卻照樣顯示總市值，會讓人誤以為自己在虧損 — 這種誤導比沒有數字更糟

交易種類：期初持股、買進、賣出、現金股利、股票股利。 現金股利計入已實現收益而不沖減成本（與券商對帳單一致）； 無償配股增加股數、總成本不變，平均成本因此自然被稀釋。

7.2 資料庫升級 v1 → v2

新增 stockTrades（索引 date、symbol）與 quotes（以代號為主鍵）。 onupgradeneeded 本來就是逐一檢查再建立，舊使用者升上來只會多出這兩個，既有資料完全不動。

備份必須同步更新。加了新的資料類型卻忘了放進備份， 使用者換手機還原後會少一整塊資料，而且完全沒有錯誤訊息。 因此 exportPayload、buildBackup、parseBackup、 replaceAllData、mergeAllData 全部一併處理， 並補上兩項測試把它釘住：一項驗證來回不遺失，一項驗證舊版備份（沒有股票欄位）仍能還原。

7.3 介面

股票區塊放在資產頁而不是新開分頁 — 股票本來就是資產的一部分，底部分頁維持五個也比較好按。

股票市值刻意不自動計入淨資產。 多數人早就用「手動估值」開了一個證券帳戶，若這裡再自動加一次就會重複計算。 重複計算的淨資產比沒有數字更危險 — 使用者不會發現自己多算了一份。 畫面上有明確說明，等第三階段能自動抓股價時，會改成由股票區塊直接更新那個帳戶的估值。
